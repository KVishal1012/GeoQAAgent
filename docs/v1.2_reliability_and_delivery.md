# GeoQA V1.2 Reliability and Customer Delivery

## Goal

V1.2 makes the first-revenue workflow dependable and easier to understand. It does not add speculative QA checks. It hardens upload-to-package delivery and makes the evidence package usable by GIS and non-GIS stakeholders.

## Reliability Improvements

- Supabase-backed approval materializes the review evidence from object storage. It does not depend on a worker-local temporary path.
- API, worker, and completed runs publish the `v1.2` runtime contract.
- `GET /api/v1/operations/health` reports storage mode, worker freshness, queue counts, failure counts, and observed worker contract versions.
- `POST /api/v1/runs/{run_id}/retry` safely requeues failed QA or package work.
- The operator console shows worker/queue health and exposes retry actions only for eligible failures.
- The release gate validates Vercel API health, Supabase configuration, worker availability, runtime compatibility, approval state, package state, and primary customer artifacts.

## Customer Delivery Improvements

`issues.csv` preserves the technical fields and now starts with these customer-facing columns:

- `Severity`
- `Finding`
- `Affected record/column`
- `Why it matters`
- `Suggested action`

The Markdown and PDF reports include an intended-use decision question, review focus, and release condition for:

- SQL/database loading
- dashboards and reporting
- GIS or asset-system migration
- routing or network analysis
- asset handoff
- spatial joins

These statements remain cautious. They describe what evidence must be reviewed and do not claim workflow suitability beyond deterministic checks.

## Release Gate

Set the protected API key and provide one completed, approved acceptance run:

```bash
GEOQA_API_KEY=... python -m geoqa.ops.release_gate \
  --base-url https://geoqa-agent.vercel.app \
  --run-id run-xxxxxxxxxxxx \
  --require-approved-package
```

The command exits non-zero if:

- API or configuration contracts do not report `v1.2`
- Supabase is not configured
- queued work has no recent worker activity
- the acceptance run is incomplete or unapproved
- package generation is incomplete
- the final PDF, Issues CSV, or handoff ZIP is missing

The same command is available through `.github/workflows/v1_2_release_gate.yml`.

## Three-Dataset Pilot

Customer data must remain outside the repository. Start from `docs/v1.2_pilot_manifest.example.json`, replace the paths and intake values, and run:

```bash
python -m geoqa.ops.pilot /secure/pilot/manifest.json \
  --output-root outputs/v1_2_pilot
```

The manifest must contain exactly three datasets. The runner writes `pilot_results.json` with the run ID, readiness result, issue count, output path, and acceptance decision for each dataset.

Pilot acceptance requires:

- all three files complete deterministic QA
- every expected report and issue artifact is generated
- the resulting readiness band satisfies the customer-specific manifest rule
- a human reviews the findings and intended-use release condition
- deployed runs pass approval, package creation, and authenticated download checks

Real customer pilot completion remains an external release gate. Sample or synthetic data cannot be reported as three customer pilots.
